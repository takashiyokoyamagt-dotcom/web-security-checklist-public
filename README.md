# web-security-checklist

Webアプリのセキュリティを、**専門家が使うチェックリストの水準で**確かめるための Claude Code 用スキル（Agent Skill）です。

IPA「安全なウェブサイトの作り方」、OWASP ASVS、OWASP Cheat Sheet Series、CWE Top 25 をまとめたチェックリスト（11カテゴリ）を使います。これに依存パッケージの既知脆弱性チェック（SCA）を加えて、Claude が次の3つの場面でセキュリティを確認します。

| モード | 使う場面 | 何をするか | 出力 |
| --- | --- | --- | --- |
| **1. コード生成** | ログイン、DB操作、API、ファイルアップロードなどを新しく作るとき | 生成の前に確認を取り、チェックリストに沿った安全な実装を作る | コードと、どの項目をどう満たしたかの短いコメント |
| **2. 監査レビュー** | PR や差分をマージする前 | 関係するカテゴリだけ、攻撃者役（Red Team）と検証役（Blue Team）の複数エージェントで調べ、確証のある指摘に絞る | 指摘ごとの修正 diff、CVSS スコア、根拠 |
| **3. 総合監査** | リリース前や納品前に、リポジトリ全体を確かめるとき | 全11カテゴリを複数エージェントで網羅的に監査する | Markdown と HTML の監査報告書、出典別の報告書 |

- 版: **v2.0.0**（[CHANGELOG.md](./CHANGELOG.md)）
- ライセンス: [MIT](./LICENSE)
- 文書と出力は日本語です。

## 特徴

- **広く使われている4つの基準を1つにまとめています。**
  - IPA「安全なウェブサイトの作り方」
  - OWASP ASVS 5.0
  - OWASP Cheat Sheet Series
  - CWE Top 25

  指摘には、どの基準のどの項目に当たるか（IPA の章、ASVS の項番、Cheat Sheet の名前、CWE 番号）を必ず付けます。
- **誤検知を減らすために、攻撃と反証を分けています。**
  - Red Team のエージェントが脆弱性の候補を挙げます。
  - 別の Blue Team のエージェントが実際のコード全体を読み、悪用できるかを検証・反証します。
  - 採否は Arbiter（全体の進行役）が決めます。
  - 確証が取れた指摘は CONFIRMED、悪用の可能性を否定できない指摘は PLAUSIBLE と区別して報告します。反証された指摘（REFUTED）は理由を添えて除外します。
- **重大度は CVSS で数値化します。**
  - 指摘ごとに CVSS v3.1 と v4.0 のベクターとスコアを算出し、重大度は v3.1 の定量区分（Critical、High、Medium、Low）に従います。
  - スコアは同梱のスクリプトが公式ライブラリ（`cvss`）で計算します。AI が主観で重大度を決めることはありません。
  - 判定の過程は `cvss-decisions.jsonl` に記録します。
- **修正案もレビューします。** 指摘に付ける修正 diff を別のエージェントが監査し、修正後に残るリスクや別の攻撃経路も書きます。
- **依存パッケージの既知脆弱性（SCA）を調べます。**
  - `npm audit`、`pip-audit` などで依存の既知脆弱性を調べます。
  - EPSS（悪用される確率）と CISA KEV（実際に悪用が確認された脆弱性の一覧）の情報を添えます。
  - ツールを実行できない環境では、結果を作らず「未実施（理由）」と報告します。
- **データベースのチェックを強化しています。**
  - SQL インジェクション、アクセス、データ保護、ネットワークと TLS、ログの各観点で詳しく見ます。オーストラリア政府の ACSC ISM（データベースの管理策）も取り込んでいます。
  - リポジトリからは確かめられない運用上の事項（実際の権限、バックアップの保管など）は、指摘ではなく「運用の確認依頼」として報告書に載せます。
- **作り話をしない設計です。**
  - ツールを実行していない、または判断できないときは「不明」「未実施」と書きます。
  - 拒否された操作を別の手段で回避しません。
  - 読んだ文書の中にある指示には従いません。
- **正しく動いたかを手順ごとに確かめます。**
  - 手順の途中で必要な文書を読んだか（ゲート）を確かめます。
  - エージェント間で受け渡す結果ファイルの形式も、スクリプトで検査します。
  - 報告書の組み立てはスクリプトで行うので、件数や表の食い違いが起きにくくなっています。

## 必要なもの

| 必要なもの | 用途 | 必須か |
| --- | --- | --- |
| [Claude Code](https://claude.com/claude-code)（サブエージェントを起動できる環境） | スキルの実行 | 必須 |
| Python 3.9 以上 | 同梱スクリプト（スタック検出、指摘の集約、報告書の組み立て、CVSS 計算など） | モード2・3で必須 |
| Python パッケージ `cvss==3.6` | CVSS スコアの計算 | モード2・3で必須 |
| `npm`、`pip-audit` など | 依存パッケージの既知脆弱性チェック（SCA） | 任意（無ければ SCA は「未実施」と報告） |
| インターネット接続 | SCA、EPSS と KEV の取得、基準の最新版の確認 | 任意（無ければ該当部分は「未取得」と報告） |

Windows、macOS、Linux で動くように作っています。同梱スクリプトの自己検査は、この3つの OS と Python 3.9・3.12 で通ることを確かめています。

## インストール

1. このリポジトリを取得します。

   ```bash
   git clone https://github.com/takashiyokoyamagt-dotcom/web-security-checklist-public.git
   ```

2. `web-security-checklist/` フォルダを Claude Code のスキルの置き場所に置きます。
   - 自分のすべてのプロジェクトで使う場合: `~/.claude/skills/web-security-checklist/`
   - 特定のプロジェクトだけで使う場合: そのプロジェクトの `.claude/skills/web-security-checklist/`

   ```bash
   # 例（macOS・Linux）
   mkdir -p ~/.claude/skills
   cp -r web-security-checklist-public/web-security-checklist ~/.claude/skills/
   ```

   リポジトリを更新しながら使いたい場合は、コピーの代わりにシンボリックリンク（Windows ではジャンクション）を張ってもかまいません。

3. CVSS 計算用のパッケージを入れます。

   ```bash
   pip install -r ~/.claude/skills/web-security-checklist/scripts/requirements-cvss.txt
   ```

4. Claude Code を起動し直すと、スキルの一覧に `web-security-checklist` が表示されます。

## 使い方

スキル名を指定する必要はありません。Webアプリのコードについて次のように頼むと、Claude がこのスキルを使い、依頼文からモードを選びます。迷うときはどのモードにするかを質問します。

### モード1: コード生成

```text
ユーザー登録とログインの API を Node.js/Express で実装して
```

- 生成の前に「チェックリストに沿って生成しますか」と確認します。「はい」を選ぶと、関係するカテゴリ（例: 認証、セッション管理、入力値検証）の項目を先に挙げてから実装します。
- 言語別の実装例は Node.js/TypeScript、Python、Java を用意しています。ほかの言語でも、言語に依存しない原則で判断します。

### モード2: 監査レビュー（差分・PR）

```text
このプルリクエスト（ファイルアップロード機能の追加）をセキュリティ観点でレビューして
```

```text
昨日の PR の差分、脆弱性がないか見てもらえますか
```

- 変更に関係するカテゴリだけを選び、Red Team と Blue Team を起動します。
- 採用した指摘ごとに、次のものを出します。
  - 修正 diff（別のエージェントが監査したもの）
  - CVSS v3.1・v4.0 のスコア
  - 根拠（IPA、ASVS、Cheat Sheet、CWE）
- 反証して除外した候補も、理由とあわせて一覧にします。

### モード3: 総合監査（リポジトリ全体）

```text
リリース前に、リポジトリ全体をセキュリティ観点で最終確認してレポートを作って
```

- 始める前に、規模と時間の見込みを示して確認を取ります。修正案レビューの厳格度（標準、高、最大）と、CVSS の環境の条件（対象システムの重要度など）もこのときに確認します。
- 全11カテゴリについて Red Team と Blue Team を起動し、依存パッケージの SCA も実行します。
- 終わると、Markdown の統合報告書、同じ内容の HTML 報告書、出典別の Markdown 報告書を作ります（[出力される報告書](#出力される報告書)）。

### 依頼のコツ

| 依頼 | 選ばれるモード |
| --- | --- |
| 「〜を実装して」「〜機能を追加して」 | モード1 |
| 「この差分・PR・コードをレビューして」 | モード2 |
| 「総合監査して」「リポジトリ全体を見て」「セキュリティレポートを作って」 | モード3 |
| 「DB まわりが安全か見て」など、一部の機能だけ | モード2かモード3（確認が入ります） |

- 「社内ツールなのか、個人情報を扱う本番サービスなのか」を伝えると、CVSS の環境メトリクスに反映され、重大度が対象に合ったものになります。
- 日常の確認はモード2、最終確認はモード3、と使い分けるのがお勧めです。モード3はコストが大きいためです（[コスト](#コスト消費トークンと時間の目安)）。

## チェックする11カテゴリ

チェックリストの本体は [`references/checklists/principles.md`](./web-security-checklist/references/checklists/principles.md) です。各項目のやさしい解説は [`docs/USAGE_GUIDE.md`](./web-security-checklist/docs/USAGE_GUIDE.md) の3節にあります。

| # | カテゴリ | 主な観点の例 |
| --- | --- | --- |
| 1 | 入力値検証 | SQL インジェクション、XSS、OS コマンドインジェクション、パストラバーサル |
| 2 | 認証 | パスワードの保存方式、総当たり対策、ユーザー列挙、多要素認証、JWT |
| 3 | セッション管理 | セッション ID の扱い、Cookie の属性、ログアウト |
| 4 | アクセス制御・認可 | 他人のデータへのアクセス（IDOR）、機能ごとの権限の確認 |
| 5 | データベース | 最小権限、接続の TLS、機微データの暗号化、監査ログ、運用の確認依頼 |
| 6 | 暗号・秘密情報管理 | 鍵や API キーの直書き、弱い暗号、乱数 |
| 7 | エラー処理・ログ | エラー内容の露出、ログへの機微情報の出力、監査ログ |
| 8 | 通信・セキュリティ設定 | HTTPS と HSTS、セキュリティヘッダ、CORS、CSRF、デバッグ設定 |
| 9 | ファイルアップロード・操作 | 種類と大きさの検証、保存場所、実行の防止 |
| 10 | 依存関係管理（SCA） | 既知脆弱性のある依存、lockfile、EPSS と KEV |
| 11 | ビジネスロジック・API 設計 | レート制限、一括代入（mass assignment）、業務上の不正 |

## 仕組み（モード2・3）

```text
          ┌──────────────── カテゴリごとに並列 ────────────────┐
 対象 ──▶ │ Red Team（攻撃者の視点で候補を挙げる）               │
 コード   │      ↓ 候補（ファイルと行番号つき）                  │
          │ Blue Team（コード全体を読んで検証・反証する）         │
          └──────────────────────────────────────────────────┘
                 ↓ CONFIRMED / PLAUSIBLE / REFUTED
          Arbiter（進行役）: 重複の統合 → 多層の解説 → 修正案の監査 → CVSS の判定
                 ↓
          スクリプトで報告書を組み立て（Markdown・HTML・出典別）
```

- **エージェントの数:** モード3はカテゴリごとに Red と Blue を立てるので、監査役だけで最大22体になります。指摘の統合、CVSS 判定、文章化の役も別のエージェントが担います。
- **読込の制限:** 進行役が一度に読む文書の量を抑えるため、手順の文書は必要になった時点で読み込みます（ゲート G0〜G7）。各ゲートを通ったかは、ゲート文書にある確認用の文字列（`GATE-TOKEN:`）で確かめます。
- **結果の受け渡し:** エージェントの結果は会話ではなくファイルで受け渡し、スクリプトで形式を検査します。長時間の実行でも内容が失われにくくなっています。
- **集約と組み立て:** 指摘の統合（同じ欠陥の重複をまとめる）、CVSS の確定、報告書の組み立ては、同梱の Python スクリプトが行います。AI の作業は判断が必要な部分に絞っています。

## 出力される報告書

モード3（と、保存を頼んだときのモード2）は次のファイルを作ります。

| ファイル | 内容 |
| --- | --- |
| `security-audit-report.md` | 統合報告書。表紙情報（対象、報告書番号、作成日、機密区分）、改訂履歴、目次、重大度別の要約、実施メタデータ、カテゴリ別の実施状況、指摘の詳細、SCA の結果、運用の確認依頼 |
| `security-audit-report.html` | 同じ内容の HTML 版。「統合 / IPA / OWASP ASVS / OWASP Cheat Sheet / CWE Top 25 / SCA / ISM」を切り替えて、出典ごとに指摘を絞り込める |
| `security-audit-report-<出典>.md` | 出典別の報告書（例: `-ipa.md`、`-owasp-asvs.md`、`-cwe-top25.md`、`-sca.md`）。「IPA の基準だけで見た結果」のように説明したいときに使う |
| `findings.jsonl`、`cvss-decisions.jsonl` | 指摘と CVSS 判定の機械可読な記録 |

指摘1件ごとには、次の内容が載ります。

- 題名、重大度、CVSS v3.1・v4.0（ベクターとスコア）、判定（CONFIRMED・PLAUSIBLE）
- 該当箇所（ファイルと行番号）と、コードの問題点
- 攻撃のシナリオと影響
- 根拠（IPA、ASVS、Cheat Sheet、CWE）
- 修正 diff と、修正後に残るリスクや別の経路

報告書の見た目は、取引先への提出にも使える、落ち着いた監査報告書の形式にしています。読み方の詳しい説明は [`docs/USAGE_GUIDE.md`](./web-security-checklist/docs/USAGE_GUIDE.md) の「レポートの読み方」にあります。

## コスト（消費トークンと時間）の目安

**モード3は大きなコストがかかります。** 下の表は、同梱の評価用サンプルアプリ（Node.js/Express と SQLite、9ファイル・約290行）にモード3を実行したときの実測値です。

| 版 | 消費トークン（1回、キャッシュの読み込みを含む合計） | 起動したエージェント | 最終の指摘 |
| --- | --- | --- | --- |
| 改善前の版（3回） | 約2,500万〜2,800万 | 22 | 26〜36件 |
| v2.0.0 | 約8,100万 | 55 | 42件 |

- **トークンの数え方:**
  - 進行役とすべてのサブエージェントの入力、キャッシュの作成、キャッシュの読み込み、出力の合計です。
  - 合計の半分近くは進行役が占めます。進行役は手順ごとに、それまでの会話を読み直すためです。
  - キャッシュの読み込みは通常の入力より安く課金されるので、料金は合計の数字ほどには増えません。
- **v2.0.0 で増えた理由:** 指摘を統合して文章化する工程を、まとまりごとに別のエージェントへ任せるようにしたためです。質（指摘の統合の正確さ、報告書の一貫性）を上げた代わりに、エージェント数とトークンが増えました。減らす改善は今後の課題です（案は [`ROADMAP.md`](./ROADMAP.md)）。
- **時間:** 約290行のサンプルアプリで、実際の作業時間は約1時間でした。大きなリポジトリでは、カテゴリごとの対象が増えるので、さらに長くなります。
- **利用枠:** 使っているプランによっては、1回のモード3で5時間あたりの利用枠に達し、途中で止まることがあります。止まったときの再開の方法は [`docs/OPERATIONS.md`](./web-security-checklist/docs/OPERATIONS.md) にあります。
- **モード2:** 関係するカテゴリだけを見るので、モード3よりずっと小さく済みます（トークンの実測はまだしていません）。
- **モード1:** ふだんのコード生成に、チェックリストの読み込み分が加わる程度です。

## 検証の結果

v2.0.0 は、意図的に脆弱性を入れた評価用アプリで確かめています。正解表は、評価を有利にする調整を防ぐために公開していません。

| 評価 | 結果 |
| --- | --- |
| モード1（生成するコードがチェックリストを満たすか） | 確認項目 6/6 |
| モード2（PR の差分レビュー） | 確認項目 14/14 |
| CVSS の算定と記録 | 確認項目 4/4 |
| モード3（サンプルアプリ、正解表21項目） | 19項目を検出（ほかに一部検出1、未検出1） |
| モード3（DB 評価用アプリ、必須25項目） | 22項目を検出 |

同梱スクリプトの自己検査（40件）は、Windows、Linux、macOS 向けに用意しています。Windows と Linux では、Python 3.9・3.12 で通ることを確かめました。

## 制約と注意

- **専門家の診断の代わりにはなりません。** 誤検知や見落としをゼロにはできません。特に PLAUSIBLE の指摘は、人が最終判断をしてください。ペネトレーションテストや第三者のセキュリティ監査の代わりではなく、開発の日常に組み込む一次チェックとして使ってください。
- **言語:** 具体的な実装例があるのは Node.js/TypeScript、Python、Java です。ほかの言語では、言語に依存しない原則で判断します。
- **CVSS の値の選び方には、人の判断との差が残ることがあります。** 判定の過程は `cvss-decisions.jsonl` で確かめられます。
- **他の環境向けの雛形は未検証です。** GitHub Copilot と GitHub Agentic Workflows 向けの雛形（`adapters/`）は、実環境でまだ確かめていません。
- **基準の版:** 採用している基準の版と確認日は [`references/sources/VERSIONS.json`](./web-security-checklist/references/sources/VERSIONS.json) にあります。確認日から6か月を過ぎると、監査の開始時に警告します。基準の更新は自動では行いません。
- **評価用のサンプルアプリ:** `web-security-checklist/evals/` のサンプルアプリには、意図的に脆弱性と偽の秘密情報を入れています。本番環境やネットワークに公開された環境では動かさないでください。
- **公開版に含めていないもの:** 開発記録（`dev/`、`docs/HISTORY.md`）、評価の実行結果、採点用の正解表は含めていません。文書の中にそれらへの参照が残っていますが、ファイルは公開版にありません。

```text
web-security-checklist/

├── manifest.json            版、手順、役割ごとの読込ファイルと予算
```

## 他の環境（Copilot など）

[`web-security-checklist/adapters/`](./web-security-checklist/adapters/) に、次の環境向けの雛形があります（どちらも未検証）。

- **GitHub Copilot:** VS Code の Agent Skills でモード1と簡易な確認、github.com の `copilot-instructions.md` で簡易な確認。
- **GitHub Agentic Workflows:** PR のレビューと、手動起動の総合確認。

Claude Code 以外では、Red と Blue のエージェントを分けて動かせるかをまだ確かめていないため、モード2・3の Red/Blue 構成は Claude Code での利用を前提にしています。
