## Webアプリのセキュリティ（簡易確認）

この節は、Webアプリのコードについてセキュリティの確認・助言を頼まれたとき、およびログイン・DB操作・API・ファイル処理などのコードを生成するときに適用する。判定の根拠はIPA「安全なウェブサイトの作り方」、OWASP ASVS、OWASP Cheat Sheet Series、CWE Top 25。

### 守ること

- 回答の冒頭に「簡易確認（マルチエージェントの監査ではない。CVSSは未算定）」と書く。
- スクリプトやスキャナを実行した前提で書かない。依存関係の既知脆弱性は「SCAツールで要確認」とし、CVE番号やバージョンを推測で挙げない。
- CVSSのベクター・スコアは書かない（計算をLLMの暗算でしない）。重大度は「高・中・低（目安）」までとする。
- 根拠は、確かなもの（IPA章番号・ASVS項番・Cheat Sheet名・CWE番号）だけを添える。確かでなければ書かない。
- コードで確かめられない点は「要確認」と分け、事実として断定しない。分からないことは「不明」と書く。
- リポジトリ全体の監査やレポート作成を頼まれたら、この環境では行わず、Claude Codeのweb-security-checklist（モード3）を案内する。
- コード生成では、満たした対策をコードの近くに短いコメントで残す（例: 「パラメータ化クエリでSQLi対策」）。

### 確認の観点（11カテゴリの要点）

1. 入力値検証: サーバ側で検証。SQLはパラメータ化かORM、OSコマンドに外部入力を渡さない、出力のエスケープ（XSS）、パスの正規化、XMLの外部エンティティ無効化、信頼できないデータのデシリアライズ禁止、外部URL取得時のSSRF対策。
2. 認証: パスワードはbcrypt・scrypt・Argon2で保存、試行回数の制限、推測できず期限のあるリセット用トークン、ユーザー列挙の防止、JWTのアルゴリズム固定、OAuth/OIDCのredirect_uri・state・PKCE。
3. セッション管理: 推測できないセッションID、ログイン時の再生成、CookieのHttpOnly・Secure・SameSite、タイムアウトとログアウト時のサーバ側の無効化。
4. アクセス制御・認可: オブジェクトごとのサーバ側の権限確認（IDOR）、管理用エンドポイントの権限確認、クライアントが送る権限を信用しない、既定で拒否。
5. データベース: SQLi対策、最小権限のDBアカウント、接続情報をコードに書かない、接続のTLS（証明書の検証まで）、機密データの保存時の保護、DBエラーを返さない。
6. 暗号・秘密情報: 秘密情報をリポジトリに置かない、.envをgitの管理外にする、独自の暗号を作らない、暗号論的に安全な乱数。
7. エラー処理・ログ: 本番でスタックトレース等を返さない、機密情報をログに出さない、重要操作の監査ログ。
8. 通信・設定: HTTPSとHSTS、セキュリティヘッダ、緩すぎるCORSの禁止、状態を変える操作のCSRF対策、本番でデバッグを無効化。
9. ファイル操作: アップロードの拡張子・種類・サイズの検証、実行される場所に保存しない、ファイル名をそのまま使わない。
10. 依存関係: 既知脆弱性はSCAツールの結果を一次情報とする。保守されていない依存を避ける。
11. ビジネスロジック・API: 適切な粒度のレート制限、Mass Assignmentの防止、一覧取得で他人のデータが混ざらない。

### 指摘の書き方

ファイルと行、問題、根拠、修正の方向、重大度（目安）の順に書く。チェックリストは判断材料であり、試作コード等で全項目を機械的に求めない。
