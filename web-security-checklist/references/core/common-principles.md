# 全モード共通の原則
本ファイルはSKILL.mdから移設した部分。本文中の「モード2手順N」「5a〜5f」「モード3手順N」「〜節」等の参照先のファイルは、SKILL.mdのモード2・モード3の必読一覧とゲート一覧（ファイルごとの担当）で引く。
<!--split:end-->
## 全モード共通の原則

- **誠実な報告**: ツールが実行できない・スキャンが未完了・判断がつかない場合は「わからない/未実施」と正直に書き、
  存在しない結果を作らない。実施メタデータ（解析日時・エージェント起動数・使用ツール等）も同じで、正確な値が
  分からなければ記憶や概算で埋めず、「不明」と書くか実測（起動回数のカウント、日時の記録）する。
- **ツールに拒否されたら別の手段で回避しない**: Writeツール等が操作を拒否した場合（例:「成果物ファイルはテキストの
  戻り値で返すべき」）、Bashのheredoc等の別の手段で代替・回避しない。拒否の事実と理由をそのままユーザー/呼び出し元
  （オーケストレータ）へ報告し、制約に従う（例: 内容をテキストとして返す、保存方法をユーザーに確認する）。
  このSKILLに沿った作業自体にも適用し、モード2/3のサブエージェントにも徹底させる。
- **サブエージェントは能動的に連絡を取らない**: モード2/3のRed/Blue Teamサブエージェントは、進捗確認や結果の受け渡しの
  ために`SendMessage`等でオーケストレータや他のサブエージェントへ連絡を取らない。結果は常にタスク完了時の
  戻り値としてのみ返す（詳細・背景はモード2の「Red Team起動→結果収集→Blue Team起動」節）。
- **根拠の明示**: 指摘には可能な限り IPA章番号 / OWASP ASVS項番 / Cheat Sheet名 / CWE番号のいずれかを添える
  （`references/sources/ipa-secure-website.md`, `owasp-cheatsheets.md`, `cwe-top25.md` 参照）。モード2/3では
  構造化タグ`sources`（`type`+`citation`のリスト）としても保持し、出典別まとめ・出典別レポートの元データにする
  （詳細はモード2手順5・モード3手順3/7）。
- **指摘は該当コードの引用と技術的な説明をセットにする**: file:lineだけでなく、該当箇所の実コードを`vulnerable_code`
  として引用し、何が具体的に問題か（`root_cause`）を攻撃シナリオ（`failure_scenario`）とは別に説明する。CONFIRMEDの
  指摘には修正案（`fix_suggestion`）を必ずunified diff形式（`-`/`+`行、変更箇所だけ）で付ける。差分にするのは、
  読者が`vulnerable_code`と見比べずに変更点を一目で分かるようにするため（詳細はモード2の
  Red/Blue Teamプロンプトの骨子）。この原則はモード2/3の**レビュー**（既存コードの欠陥の指摘）に適用し、モード1の
  **生成**（欠陥のないコードを新規に書く）にはそのまま当てはめない。モード1では手順2の「満たすべき項目を実装前に
  短く列挙」「該当箇所に根拠をコメントで残す」を対応する適用先とする。
- **説明は読者層に応じて多層化し、修正案は監査レビューを経てから提示する**: Red/Blue Teamの簡潔な技術的フィールド
  （`root_cause`/`failure_scenario`）に加え、Arbiterが採用指摘ごとに専門知識を前提としない解説（`plain_explanation`）・
  技術的詳細解説（`technical_detail`）・該当コードの問題点（`code_issue_annotation`）・修正内容の解説（`fix_explanation`）
  を書き、技術者・非技術者の両方の読者が理解できるようにする（詳細はモード2手順5d）。確定した`fix_suggestion`は
  必ず監査レビュー（`fix_audit_*`）で機能することを検証してから報告書に載せる（詳細はモード2手順5e・
  「修正案監査レビューの厳格度」節）。
- **重大度はCVSSの定量的区分を正とする**: Arbiterの主観で決めず、採用指摘ごとにCVSS v3.1・v4.0のベクターを技術的根拠に
  基づいて判定し、`scripts/calculate_cvss.py`で算出したスコアの重大度区分（v3.1を正、v4.0は併記）をそのまま採用する
  （詳細はモード2手順5f・「CVSSスコアの算定」節）。算出できない場合は推測で埋めず、その旨を正直に報告する。
- **推測より実証**: Red Teamの指摘はBlue Teamが実コードの文脈（呼び出し元・ミドルウェア・既存のサニタイズ処理等）で
  検証してから採用し、推測だけでCONFIRMED/REFUTEDと判定しない。SCAも可能な限り実際にツール（`npm audit`等）を実行し、
  実行できない場合のみ`dependency-sca.md`に従って推測ベースであることを明記する。この裏取りが単純なチェックリスト
  適合確認との最大の違いである。「再現しなかった」を根拠に評価を下げる条件は`references/core/agent-roles.md`「非再現を根拠にした評価の引き下げ」に従う。実証に必要な追加ファイルの読み込みは
  下記の「コスト意識」より優先して許容する（ただし無制限にリポジトリ全体を読み漁らない）。
- **過剰な足かせにしない**: チェックリストは判断材料であり、機械的な全項目強制ではない。適用する項目の範囲・厳格さは
  リポジトリの性質（社内ツール／個人情報を扱う本番サービス等）に応じて調整してよい（重大度は含まない。
  重大度はCVSSの定量的区分を正とし、リポジトリの性質・システムの重要度は「CVSSスコアの算定」節の環境メトリクス
  確認で反映する）。
- **コスト意識**: モード2は関連カテゴリのみに絞る（`category-map.md`）。モード3は全カテゴリ対象だが、各サブエージェントには
  関連ファイルだけを渡し、リポジトリ全文を毎回読ませない。モード2/3とも、着手前にユーザーへ規模感（起動するエージェント数・
  概算所要時間）を一言伝えてから始める。
