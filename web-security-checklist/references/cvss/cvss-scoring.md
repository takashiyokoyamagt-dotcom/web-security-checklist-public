## CVSSベクターの判定基準

Red/Blue Teamが既に確定した`technical_detail`・`failure_scenario`・`vulnerable_code`・`category`の
内容から、以下の基準でベクターの各メトリクスを判定する。判定した値と、その根拠（技術的事実の
どの部分から導いたか）を1メトリクスにつき1行程度で記録する（`assets/templates/report_template.md`6節の
プレースホルダ名に合わせ、メトリクス単位で`cvss_v3_{メトリクス名}_reason`（例:
`cvss_v3_AV_reason`、v3.1の8メトリクス分）・`cvss_v4_{メトリクス名}_reason`（例:
`cvss_v4_AV_reason`、v4.0の11メトリクス分）として保持し、後述のリスク分析章でそのまま使う。
1つの集約フィールドにまとめない）。**根拠文は指摘ごとに、LLMがコード上の事実（行・入力・結果）から考察して書く。スクリプトでの一括生成や、複数指摘への同一文の流用はしない。****推測で埋めず、`failure_scenario`に書かれた具体的な攻撃経路・
前提条件に基づいて判定すること**。
**判定根拠の重複禁止**: 同一指摘内で別メトリクスに同じ文・言い換え程度の文を書かない。指摘間でも使い回さない
（事実が似ていても、その指摘のルート・行・入力・結果で書く。C/I/A・VC/VI/VA・SC/SI/SAは、そのメトリクス固有の帰結（何が起きる/起きないか）で書く）。`check_cvss_decisions.py --report`は、規則タグの接頭辞と「（根拠: …）」を除いて比べ、同一指摘内の
40字以上の同一/類似（類似度0.9以上。C/I/A等の対同士はWARN）と、6節全体の根拠の異なり数が60%未満（40行以上）をNG、20字以上の短文の重複・
同じ根拠（セル全体）を4指摘以上で使うこと・同じ文（1文）が3指摘以上にあること（文単位の流用）・異なり数85%未満をWARNにする。`m3`の事実欄の別メトリクス間重複と、`--final`で基準ベクターが異なる指摘の`v4diff.why`の同文もWARN（事実を入れて書き直す）。

**CVSS v3.1（Base）**:

| メトリクス | 値 | 判定の目安 |
| --- | --- | --- |
| AV（攻撃元区分） | N/A/L/P | ネットワーク越しに到達可能ならN。同一セグメント内のみならA。ローカル環境が必要ならL。物理アクセスが必要ならP |
| AC（攻撃条件の複雑さ） | L/H | 攻撃者が意図的に用意できる条件のみで再現可能ならL。攻撃者の制御が及ばない特殊な条件（競合状態、特定の設定等）が必要ならH |
| PR（必要な権限） | N/L/H | 未認証で到達可能ならN。一般ユーザー権限が必要ならL。管理者等の高い権限が必要ならH |
| UI（ユーザー関与） | N/R | 攻撃者の操作だけで完結するならN。被害者に何らかの操作（リンクを踏む等）をさせる必要があればR |
| S（スコープ） | U/C | 脆弱なコンポーネント自身の権限の範囲内で影響が収まるならU。それを超えて別のコンポーネント・別ユーザーのリソースに影響するならC |
| C/I/A（機密性/完全性/可用性への影響） | N/L/H | `failure_scenario`で実際に読み取り・改ざん・停止のどれが生じるかに基づき、影響なし(N)／部分的(L)／重大(H)を判定 |

**CVSS v4.0（Base）**: v3.1と多くが対応するが、以下の点が異なる。

| メトリクス | 値 | 判定の目安 |
| --- | --- | --- |
| AV/PR/UI | (v3.1と同様の区分) | 同上の基準を適用（UIは v4.0 では N/P/A の3区分。Pは受動的関与、Aは能動的な複数操作が必要な場合） |
| AC（攻撃条件の複雑さ） | L/H | v4.0ではAC自体は攻撃者側が制御できない技術的な障壁（防御機構の回避難度等）のみを指し、環境条件はATに分離される |
| AT（攻撃条件・前提） | N/P | 追加の前提条件（特定のタイミング、被害者側の特定の設定・状態等）が不要ならN。必要ならP |
| VC/VI/VA（脆弱コンポーネント自身への影響） | H/L/N | 脆弱性のあるコンポーネント自体への機密性/完全性/可用性の影響 |
| SC/SI/SA（波及先への影響） | H/L/N | 脆弱なコンポーネントを踏み台に、それ以外のコンポーネント・データへ影響が及ぶ場合の機密性/完全性/可用性への影響（v3.1のScope:Changedに相当する概念をより詳細に表現したもの） |

## 影響・権限メトリクスの判定原則

上記「判定の目安」を補う。既存の記述と衝突する場合は、本原則を「判定の目安」の具体化として優先する。

- **判定の軸**: 「アプリ自身の権限で、コードに実在する欠陥経路から攻撃者が実際に行えること」で判定する。
  他の脆弱性との連鎖、将来の実装変更、コードに現れない運用条件は根拠にしない。例外は次の3つのみ: PR（下記）、AC/AT（防御不足。下記）、I規則の認可属性
  （消費側の判定が未使用でも、列定義・JWTのclaim等に存在することで採る）。
- **C**: 攻撃者に渡るデータが、認証情報・個人情報（メールアドレスを含む）・テーブル全件に及べばH。
  バージョン・パス・存在有無・非機微な1件程度ならL。連番ID等で全件を列挙できる場合は全件とみなす。
- **I**: 任意のレコードを変更・削除できる、または認可属性（role/is_admin/owner_id等）を書き換えられれば
  H。自分のレコードや非認可属性のみならL。認可属性か否かは、列名・JWTのclaim・コメント・エンドポイント
  名などコード上の意味で決める。その属性を消費する認可判定がコードに無いことは、Iを下げる理由にしない
  （未使用は別の欠陥であり、属性の意味は現に存在する）。
- **A**: 1回の攻撃でサービスまたは全件データが使えなくなる（全件DELETE、プロセス停止、ディスク枯渇）ならH。
  遅延のみならL。ただしSELECT系SQLiの既定はA:Nとし、DoSを実証できた場合のみLとする。
  実行文がSELECTのみで複文不可のドライバなら、SQLiでもI/AはNとする。
- **PR**: 認証機構がなければN。認証はあるが役割・所有者チェックがなければL。管理者限定ならH。
  例外: 別のバグで現状到達不能な認証経路（認証機構の欠落等）も、意図された機構が機能する前提でPRを
  採点する。ただし現状の到達不能性は指摘本文に必ず明記する（ACやATでは表現しない）。
- **AC/AT**: ソースや秘密値がリポジトリ内に平文である場合、その入手をH/Pの根拠にしない。他の脆弱性の
  併存が前提の防御不足に限りAC:H。v4.0では原則AT:Pに移す。ACをHにするのは防御機構の回避を要する場合のみ。
  攻撃者が自力で作れない条件（下の「前提条件の確認」の(d)）も、v3.1ではこの原則どおりAC:Lのままとして
  ACの判定根拠にその旨を書き、v4.0ではAT:Pとする（同節）。
- **S**: 既存S行の「別ユーザー」は、権限領域を超える場合に限る。同一の認可領域内の他ユーザー（IDOR、
  SQLi）はU。ブラウザ（XSS）や内部ネットワーク（SSRF）のように領域を超えればC。
- **UI**: 被害者が1回の操作（リンクを開く・ページを閲覧）で足りればR（v4.0はP）。ファイルの配布・貼付など
  複数の能動的操作が要る場合のみv4.0でA（v3.1はR）。
- **迷ったときの規則**: 「コードで確認できた最大の影響」を採る（grep・実測・Blue Teamの裏取り）。
  確認できない上位の影響は採らず、可能性として当該`_reason`に書く。
- **未使用の欠陥**: 参照0件のコード・設定も、表と原則どおりに採点する（Nに倒して採点を省かない）。そのうえで指摘本文と7節に「現状は未使用のため実質問題なし」と明記する。**未使用と呼べるのは、その欠陥が成立する入力経路・呼び出し元が現状コードに存在しない（コード上の到達不能）場合だけ**。必要な防御機構が存在しないこと（認証機構・入力検証・認可チェック・レート制限・ログの不在）は未使用ではなく、通常の欠陥として採点し「実質問題なし」と書かない。
  - 未使用の例: 定義だけで参照0件の定数・関数（秘密値は、ダミー/サンプル値で実鍵でないと確認できる場合に限る）、登録・マウントされておらず外部から到達する経路が無いハンドラやルータ、読み込まれない設定ファイル。
  - 未使用でない例: 登録済みのHTTPルート（外部から直接到達できる）、認証機構の不在（公開ルートが無防備）、入力検証の欠如（入力は現に届く）、認可チェックの欠落、読み込まれて実行される設定の不備、実在の認証情報や本番・他システムと共有される鍵のハードコード（参照0件でもリポジトリ閲覧者への漏えい自体が問題）。
  - 判定質問（全て「はい」のときだけ未使用）: ①その欠陥のコードへ至る到達経路（HTTPルートの登録・マウント、内部の呼び出し元、設定の読込）をgrepで探して0件か。②悪用される入力を、現状コードの別の経路から届けられないか。③問題は「あるものが使われていない」ことで、「あるべきものが無い」ことではないか。④秘密値なら、ダミー/サンプル値で実鍵・本番や他システムと共有される鍵でないと確認できるか。
  - 該当時は確定行に`unused:true`と`unused_why`（grep式→参照0件）を書き、報告書の5節では見出し「実害の有無」の直下に定型句を書く（checkerはこの見出し名で探す）。並びは`finding-final.md`5f、5cのベースは`finding-arbiter.md`、表示は`report_template.md`に従う。
- **v3.1→v4.0**: C/I/A→VC/VI/VA。S:Cの影響はSC/SI/SAへ移し、脆弱コンポーネント自身にも及ぶ影響のみ
  VC/VI/VAに残す（XSSはVC/VI:N＋SC/SI、SSRFで内部サービスの応答を読むならSC）。UI:R→UI:P。

## 類型別の基準ベクター（既定値）

v3.1の値（AV:N、UI:Nを前提とし、異なる場合のみ明記）。表の値は既定であり、逸脱する場合は該当メトリクスの
`_reason`の先頭に「基準からの逸脱: 」とコード上の根拠を書く。根拠なしの逸脱と、表のみを理由とする採点は不可。

| 類型 | AC/PR/S | C/I/A | 根拠・注記 |
| --- | --- | --- | --- |
| SQLi（SELECT・複文不可） | L/N/U | H/N/N (7.5) | UNION・エラーで全表を読める。書込み不可。Aは実証時のみL |
| SQLi（書込み文、または複文可） | L/N/U | H/H/H (9.8) | 全件改ざん・削除が可能。blind読取りも成立 |
| 格納型・反射型XSS | L/N/C, UI:R | L/L/N (6.1) | v4はVC/VI:N・SC/SI:L、UI:P。格納型でもUI:R |
| IDOR（他人の参照・更新） | L/L/U | 項目の機微性でH/L | 連番ID等で全件列挙可なら全件。メール・パスワード・トークンを含めばH。更新はI |
| 認可欠如（認証済・役割チェックなし） | L/L/U | 操作の影響で判定 | make-adminはI:H（is_adminは認可属性）(6.5) |
| 認証欠如 | L/N/U | 機能の影響で判定 | 全件返却C:H (7.5)、全件DELETE I:H/A:H (9.1) |
| Mass Assignment | L/入口に従う/U | 認可属性ならI:H、他はI:L | C・AはN。属性の意味はI規則で判定 |
| ハードコード秘密（JWT鍵等） | L/N/U | 迂回される認証の背後の全機能のC/I/Aの和 | 認証背後の全エンドポイントを列挙し`_reason`に記載。ソースの一部しか無く列挙できない場合のみ、上限としてH/H/N。PR例外の拡張として、認証機構の欠落等で背後の機能が現状到達不能でも、意図された認証機構が機能する前提で背後のC/I/Aを数える（到達不能性・未使用の旨は指摘本文に明記）。 |
| 平文・弱いパスワード保存 | H/N/U | H/N/N (5.9) | DB入手が前提。入手経路が同レポート内の別指摘（全件取得API・SQLi等）ならAV:N/PR:N。ホストやバックアップ経由のみならAV:L/PR:H |
| 無制限アップロード | L/N/C, UI:R | 静的配信のみ: L/L/N (6.1) | サーバ実行可なら S:U, UI:N, H/H/H (9.8)。サイズ無制限は別指摘でA:H |
| SSRF | L/N/C | 応答が返る: H/N/N (8.6) | blindはL/L/N。v4は応答の機密をSC側へ置く |
| パストラバーサル | L/N/U | 読取: H/N/N、書込: N/H/N | 範囲がディレクトリ内に限られればLに下げる |
| エラー・情報露出（スタック、パス、版） | L/N/U | L/N/N (5.3) | 認証情報・全件データが混じれば別類型で判定 |
| 防御不足（Cookie属性、CSP等のヘッダ、JWT有効期限） | H/N/U | L/L/N | 他の脆弱性の併存が前提。UIは併存する攻撃が操作を要すればR（Cookie属性・ヘッダ）、不要ならN（JWT有効期限）。v4はAT:P |
| 脆弱な依存パッケージ | 勧告のベクターを起点 | 勧告どおり | 使い方が悪用条件を満たさなければAC:H（v4はAT:P）とし、影響は最大L。ただし条件を満たさない根拠は`dependency-sca.md`「到達可能性」を満たすこと（再現しなかっただけでは下げない） |

CORS全許可・ユーザー列挙・試行回数制限なしは表の対象外とし、上記原則から個別に判定する（既定値は置かない）。

## 前提条件の確認（必須。判定の直後、作業メモ行を書く前）
指摘ごとに、評価を制約する次の前提の有無を確かめ、判定記録の`prem`に書く（値は`yes`＝その前提が有る／`no`＝無い／`unk`＝不明／`na`＝その指摘の種類に当てはまらない。`yes`・`no`の根拠は`file:line`か`grep:式→件数`。`yes`・`unk`は説明も書く。`na`の根拠は`-`でよい）。(a)開発依存・ビルド時のみで本番に載らない（devDependencies等。AV・AC/ATと「到達可能性」。依存・ビルド・開発ツールに関わらない指摘は`na`）。(b)防御となる既存の仕組みがある（lockfile・integrity・`npm ci`・CIの版固定等。AC/AT。依存の導入・配布の経路に関わらない指摘は`na`）。(c)漏れる値・悪用に使う値が、この指摘とは別の経路（リポジトリへの直書き等）で既に公開済みで、この指摘で新たに漏れるものではない（秘密値の直書きの指摘自体は`no`。C、v4はVC。値の漏えい・既知の値の悪用を含まない指摘は`na`）。(d)攻撃者が自力で作れない条件（障害・エラー・特定の状態）が要る（v4はAT。v3.1は上の原則「AC/AT」どおりAC:Lのままとし、理由を書く。成立に特別な条件の要らない指摘は`na`）。(e)攻撃の起点がホスト／ローカルへの侵入を前提とする（ネットワークから届かない。AV）。(f)現状は実害が無く、将来の付け忘れ・設定変更を仮定した評価である（上の「判定の軸」。将来の実装変更は根拠にしない）。(e)(f)は全ての指摘に当てはまるので`na`にしない。
書式: `"prem":{"a":["yes","package.json:41","devDependenciesのみ"],"b":["yes","package-lock.json:4386","integrityあり"],"c":["na","-",""],"d":["no","a.js:9","入力で起こせる"],"e":["no","server.js:3","公開ポート"],"f":["no","a.js:9","現に到達"]}`（6項目すべて。メモ行・確定行とも）。`yes`・`unk`が1つでもあれば、その前提をどのメトリクスの選択にどう反映したか（反映しないならその理由）を、該当メトリクスの`_reason`（6節の該当行の判定根拠）に「前提(a): …」の形で書く。(d)が`yes`なら、v3.1のACの判定根拠に「前提(d): …のためAC:Lのままとする（理由）」を、v4.0はAT:Pにする（しないなら理由をATの判定根拠に）。この確認は既存の原則・基準表を変えず、重大度を機械的に下げるものでもない（引き下げは原則・基準表・`dependency-sca.md`「到達可能性」の条件に従う）。前提を確かめた記録を残し、前提と矛盾する値の選択を見つけるためのものである。該当行に「前提(x)」の反映を書いた判断はWARNにならないので、2節で「残したWARN」として説明し直す必要は無い。確認の結果Arbiterが値を変えたら「Arbiterが値を上書きしたときの再確認」を行う。(c)は「AC/AT」の原則（秘密値の入手をH/Pの根拠にしない）と別の観点（影響）で、(f)の`yes`は「未使用の欠陥」とは別である（到達経路はあるが現状の害が無い。未使用かは判定質問で決める）。委任時は、サブエージェントが返す作業メモ行にも`prem`を書かせる。
検算: `check_cvss_decisions.py`は`prem`の形式の誤り（(e)(f)の`na`を含む）をNGにし（`--append`も拒否する）、`yes`の前提と矛盾しうる値のうち、6節の該当メトリクスの判定根拠に「前提(x)」が無いものをWARNにする。v3.1とv4.0を別々に見る: (a)AV:NかつAC:L（v4はAV:NかつAT:N。AV・AC／AV・ATの行）、(c)C:H（v4はVC:H）、(d)AC:L（v4はAT:N）、(e)AV:N。`--report`なしでは値だけでWARNにする。`yes`・`unk`の「前提(x)」が6節の当該指摘のどこにも無い、`prem`が一部の指摘にだけある、もWARN。新規の実行では`--require-prem`を付け、`prem`の無い有効行をNGにする（`prem`の無い旧形式の記録の再検査では付けない）。

## ベクターの整合性確認（必須。`scripts/calculate_cvss.py`の実行前に行う）

全指摘のベクターを判定し終えたら、次を行う。

1. `category`のCWE番号ごと、および同一の影響（同じ属性・同じデータ）を持つ指摘ごとにグループ化し、
   ベクターが同一であることを確認する。異なる場合は、差を生むコード上の事実（文の種類、認証の有無、
   データの機微性等）を該当メトリクスの`_reason`に追記する。追記できない差は値を揃える。
2. 同一エンドポイントに複数の指摘がある場合（認証欠如とSQLi等）は、5b/5cで確定済みの統合結果を前提に、
   統合の対象か確認する（モード2手順5b）。統合しないなら、それぞれの影響が自身の欠陥だけで説明できることを確かめる。
3. v3.1とv4.0の対応規則（C→VC、AC:H→AT:P、S:C→SC/SI/SA）が全指摘で同じように適用されているか確認する。
4. モード3のバッチ処理では、この確認はArbiterが全バッチのベクター確定後に一度だけ実施する。
5. 結果を`cvss_consistency_note`（1〜3行、全指摘で1つ）に記録し、報告書6節冒頭に転記する。
   例:「CWE-89の2件は文種別の違い（SELECT／DELETE）によりC/I/Aのみ相違。他は同一」。

## Arbiterが値を上書きしたときの再確認（必須）

実機検証・Blue Teamの訂正・自己点検などで、Arbiterがサブエージェントや前revのメトリクス値（ベクター）を変えた指摘は、確定行を書く前に次の5点を再確認し、確定行の`rechk`に`["reason","body","sections","rank","flags"]`の5語を全て書く（確認の結果、変更が要らない点も確認済みとして書く）。
上書きは、raw追記と確定行の前（整合性確認の段階）に確定する。raw追記の後で値を変えたときは、その指摘の主ベクターと別案を新ベクターで再実行し、`--append-raw`で再追記する（同じ`id`の主行は最後の行が有効で、checkerはWARNを出す）。そのうえで`rev+1`のメモ行（`rev_why`必須）→確定行の順に書き、確定行の`raw`は再追記した主行の行番号にする（`--fill-ids`が後埋め）。

1. reason: その指摘の他メトリクスの`_reason`と`m3`の事実が、旧い値・旧い前提（例:「PoC未実行」）を引いていないか。v3.1を変えたらv4.0の対応メトリクスと`v4map`も。
2. body: 概要・技術的詳細解説・攻撃シナリオ・わかりやすい解説・該当コードの問題点・修正内容の解説が、旧い影響・条件を述べていないか。
3. sections: 他節の当該指摘の記述（1節の件数表・エグゼクティブサマリー、4節の表、7節、8節SCA表、9節、10節の次のアクション、2節、HTML・出典別）。スコア・重大度・「最上位」等の表現。
4. rank: 5節の順位と番号。帯が変われば並べ直し、一時ID対応表・`id`・`grp`・他指摘からの相互参照を直す。
5. flags: `v4diff`・`sbs`・`attn`・`borderline`。帯が変われば別案を主ベクターから作り直して再算出する。

検算: `--report`付きの`check_cvss_decisions.py`が、報告書の4・5・6節のスコア・重大度・メトリクス値を確定行・raw出力と照合し（不一致はNG）、値を変えた指摘に`rechk`が無ければWARN（`--strict`ではNG）、項目が欠ければNG。文章（reason・body）の整合は検査できないので、Arbiterが読んで確認する。

## スコアの算出

判定したベクターを`CVSS:3.1/AV:.../A:H`・`CVSS:4.0/AV:.../SA:H`の形式（環境メトリクスを反映する
場合はCR/IR/AR等も同じ文字列に追記）に組み立て、`scripts/calculate_cvss.py`
（`pip3 install -r scripts/requirements-cvss.txt`で依存パッケージを導入済みであること）を
Bashで呼び出してスコアを取得する:
```bash
python3 scripts/calculate_cvss.py --v3-vector "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H" --v4-vector "CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N"
```
出力のJSONから`v3.base_score`/`v3.base_severity`（環境メトリクスを反映した場合は
`v3.environmental_score`/`v3.environmental_severity`も）と`v4.score`/`v4.severity`を取得し、
指摘の`cvss_v3_vector`/`cvss_v3_score`/`cvss_v3_severity`/`cvss_v4_vector`/`cvss_v4_score`/
`cvss_v4_severity`フィールドに記録する。環境メトリクスを反映した場合は環境スコア・環境重大度を
「正」として使う（`cvss_v3_severity`にはこちらを入れる）。重大度(Critical/High/Medium/Low)は
この`cvss_v3_severity`をそのまま採用する（CVSSの"None"区分に該当する場合はLowとして扱う。読み替えるのは見出し・4節の重大度列・1節の件数表だけで、v3.1・v4.0のスコア欄は計算どおり「0.0（None）」と書き、件数表の下に「CVSS v3.1のスコアが0.0（None）のn件はLowに数えている。」を足す〔0件なら省く〕。`--report`が検算する）。

**スクリプトがエラーを返した場合（`error`フィールドが含まれる場合）**: スコアを推測で埋めない。
エラーが出た版（v3のみ／v4のみ／両方）に応じて次のように扱う。v3とv4は別々に判定する（算出できた方はそのまま使う）:
- **v4のみエラー**: `cvss_v4_*`には「CVSS v4.0未算出（理由: <errorの内容>）」と記録する。
  `cvss_v3_*`は算出できているので、重大度は`cvss_v3_severity`をそのまま採用する（フォールバックなし）。
- **v3のみエラー、または両方エラー**: `cvss_v3_*`（該当すれば`cvss_v4_*`も）に
  「CVSS未算出（理由: <errorの内容>）」と記録する。重大度は`cvss_v3_severity`が算出できないため、
  モード2手順4（`references/pipeline/finding-arbiter.md`）で暫定保持していたRed/Blue Teamの`severity`を「Red/Blue Team判定（CVSS v3.1未算出のため
  暫定）」と明記した上でそのまま使う。
存在しないスコアを捏造しないことを優先する（「誠実な報告」の原則）。

**スクリプト実行の徹底（v3.1/v4.0の一方だけを実行して他方を推測・近似値で埋めない。「誠実な報告」の原則）**:
`scripts/calculate_cvss.py`は指摘ごとにv3.1・v4.0とも実際に実行し、出力のJSONを確認してから
転記する。件数が多ければ1回のループでまとめて実行し、結果をJSON Linesへ追記してよい（各行は確認する）。
モード3は判定記録の③④を`python3 scripts/cvss_finalize.py --work <保存先> raw`・`final`で行う
（別案の算出値がメモ行と違うWARNはメモ行を`rev+1`で直して再実行。確定行の`v4diff.why`が実際の差の
原因と違えば`rev+1`で直す）。メトリクスの判定はサブエージェントに分担してよいが、スクリプトの実行と
転記は**Arbiterが一括して行う**か、サブエージェントに実行させるなら正確なコマンドと生のJSON出力を
残させ、Arbiterが転記前にベクターとの対応を検算する。

## 判定記録（`cvss-decisions.jsonl`。人間レビュー用。本文には載せず2節から参照）
一次情報源はメトリクスの判定文＝`_reason`（報告書6節）。本記録は値・証拠の所在・棄却案・注意度だけを持ち、理由文は複製しない（`dev`はメトリクス名のみ。理由は`_reason`先頭の「基準からの逸脱: 」）。自由文欄に一時IDを書かない。
全行（メモ行・確定行、`cvss-raw-output.jsonl`の行）に`seq`（1始まりで欠番のない連番）と`ts`（UTC、ISO 8601）を付ける。時刻を手書きせず、追記は`python3 scripts/check_cvss_decisions.py --append <ファイル>`（stdinにJSON Lines）か`--append-raw <ファイル> --id <tmp> [--kind alt --of <メトリクス>]`（stdinに`calculate_cvss.py`の出力）で行うと自動で付く。並列に呼ばない（排他ロックでseqの重複とtsの逆行は防ぐが、行の順序は不定になる。システム時計の巻き戻しまでは防げない）。checkerはPython 3.9以上で動く。
書込みは2段。まず判定直後に作業メモ行（`st:"memo"`。`id,grp,band,sbs,attn,calc,raw`はnull可）を`findings-log.jsonl`と同じ保存先へ追記。整合性確認で値を変えたら`rev+1`の作業メモ行（`rev_why`必須）。次に、整合性確認→バッチループ（主ベクター・別案とも）の後に確定行（`st:"final"`、`rev`は同じ`tmp`の既存行（メモ・確定とも）の最大+1以上。メモ最大rev以下では有効行がメモ行のままになる。`--append`は拒否する）を追記。有効行は同一`tmp`の最大rev。
キー: `tmp`（統合時`I3+U1`。5bの一時ID〔`make_idmap.py`が出す対応表TSVの第1列と同じID〕を昇順に`+`で連結した形で、群の作業用IDではない。`--idmap`のキーと同じ文字列。`--mapping`は構成IDの集合で照合する）,`cat`,`cwe`[],`type`（基準表の行名。無ければ「表外」）,`v3`,`v4`（全文。算出エラーは「未算出」）,`m3`,`v4map`（`std`か逸脱1行）,`dev`,`borderline`,`by`（arbiter/sub/post）,`rev`,`st`。確定行はさらに`id`（最終番号`5.N`。`--fill-ids`で後埋め）,`unused`・`unused_why`（未使用の指摘のみ。前述）,`rechk`（値を上書きした指摘のみ。例: `"rechk":["reason","body","sections","rank","flags"]`。前節）,`grp`（同一CWE・同一影響は同名）,`band`（採用重大度。v3.1がNone(0.0)なら`Low`。見出し・4節の重大度列・HTMLの`cvssV3Severity`も同じ。スコア欄は「0.0（None）」のまま〔前述〕）,`sbs`,`attn`,`calc`（`std`か実行全文）,`raw`（後埋め）。`v4diff`は、v3.1の基準値の帯（環境メトリクス反映時も基準値。None→Low）とv4.0の`severity`（None→Low）が異なるときだけ必須: `{"cause":"spec","why":"差が出たv4メトリクス名（AT/SC/SI/SA/UI等）と1行の理由"}`。`spec`＝版の基準の違いで説明できる（`v4map`が`std`のときのみ）、`judgment`＝同じ事実の読み違いの疑い。帯が一致する指摘、v3.1かv4.0が未算出の指摘には書かない。v4固有の非標準判断のみ`m4`。メモ行・確定行とも`prem`（前提条件の確認。書式は「前提条件の確認」節。新規の実行では必須で、無い旧形式の記録も読める）。
`m3`は8メトリクス全部を`"AV":["N","routes/search.js:8","公開GET","default"]`（値／証拠`file:line`（`a.js:9,10`可）か`grep:式→件数`／その行が示す事実40字以内／規則タグ）で書く。規則タグは`default`,`表:<行名>`,`原則:<名>`,`迷:`,`例外:`,`逸脱:`のいずれかで始める。`迷`＝「迷ったときの規則」を使った、または本文で2通りに読めると述べた。`例外`＝PR例外・AC/AT規則。`逸脱`＝基準表の既定と異なる。`逸脱`は`dev`へ、`迷`・`例外`・`逸脱`は全て`borderline`へ入れ、`borderline`の各メトリクスは棄却した別案を5要素目`{"alt":"L","score":"6.5/Medium","why":"20字"}`で必ず持つ（別案ベクター＝主ベクターの当該1メトリクスだけ差し替え。スクリプトで算出し推測で書かない。全単一メトリクス代替は14通り中約11通りで帯が変わるため使わない）。`sbs`＝別案のいずれかでv3.1の帯が変われば true。`attn`＝sbsならhigh、`v4diff`がjudgmentならhigh、`borderline`非空ならlow以上、他はnone。非noneは`attn_why`1行。
