7. **出典別Markdownレポートの作成**: 手順3で保存済みのデータファイルを`Read`ツールで読み直し
   （手順5作成時点の会話コンテキストに頼らない。手順5実行からある程度ターンが経過しており、
   ハーネス側の自動要約が挟まっている可能性があるため）、そこに付与した`sources`をもとに、
   指摘が1件以上ある出典それぞれについて、`assets/templates/report_template_by_source.md`の構造で
   個別のMarkdownファイルを手順5で合意した保存先に追加保存する（例: `security-audit-report-ipa.md`,
   `security-audit-report-owasp-asvs.md`, `security-audit-report-owasp-cheatsheets.md`,
   `security-audit-report-cwe-top25.md`, `security-audit-report-sca.md`。手順5のMarkdown保存自体が
   拒否されテキスト応答のみで完了していた場合も、ユーザーと合意済みの保存先ディレクトリ自体は
   変わらないため、そこに保存を試みる）。ファイル名の出典部分は`ipa` / `owasp-asvs` /
   `owasp-cheatsheets` / `cwe-top25` / `ism` / `sca`のスラッグを使う。モード3は
   `python3 scripts/render_by_source.py --work <保存先> --target <対象> --mask-file <追加の秘密値> --out-dir <保存先>
   --repo-name <名称> --date <日付> --sca-raw <SCA出力>`で作り（スクリプトを書かない）、出力の行を統合レポート末尾に貼る。

   **`{{unified_report_finding_number}}`欄の埋め方**: `assets/templates/report_template_by_source.md`の
   `{{unified_report_finding_number}}`欄（統合レポート上の該当指摘番号）は、モード3手順1で
   作成した一時ID↔最終報告書番号の対応表を参照し、その対応表の値のみを根拠に機械的に転記する。
   手順3で用いた一時ID（`F`番号等）をそのまま統合レポートの節番号とみなして転記しないこと。また、
   IPA/OWASP ASVS/OWASP Cheat Sheet等の出典・章番号（`citation`）は、5aで既に確定した`sources`
   タグの値をそのまま使用し、この手順7の時点で独自に出典・章番号を再判定しない
   （例えばOWASP ASVSの章番号を5aと異なる値に再解釈するなど）。
   各出典内の並びは統合レポートに合わせる（同じ重大度の帯では未使用の指摘を末尾に置き、判定欄に「（未使用・実質問題なし）」を付ける。`references/pipeline/finding-final.md` 5f「並び順」）。
   各出典内でのグルーピング方法は出典ごとに異なる（`assets/templates/report_template_by_source.md`参照）:
   IPAは`references/sources/ipa-secure-website.md`**1章**の脆弱性名別（3章ではない。3章は失敗例集であり
   本SKILLの根拠引用には使わない。2章を引用した指摘は1章の後ろの2章のグループに置く）、OWASP ASVSは章番号別、OWASP Cheat Sheetはシート名別、
   CWE Top25はCWE番号別、SCAは2節を使わず3節の3.1個別指摘・3.2生出力（付録）に分ける。指摘の詳細
   （該当コード・該当コードの問題点・わかりやすい解説・技術的詳細解説・攻撃シナリオ・修正案・
   修正内容の解説・修正後に残るリスクと別経路（あれば）・修正案の監査レビュー）は統合レポートと同じ粒度を保ち、出典別だからといって
   情報を削らない（SCAも例外ではなく、Red/Blue Teamが検証した個々の依存関係脆弱性の指摘を
   スキャンツールの生出力とあわせて記載する）。該当指摘が0件の出典（手順6（`references/modes/mode3-html.md`）と同じ判定基準）は
   ファイルを作らず、統合レポートの末尾（後述）にその旨を一言記録する。各出典別レポートの
   サマリー表も、手順5と同様にその出典に該当する指摘一覧を実際に数え直して件数を算出する
   （統合レポートの全体件数をそのまま流用しない。出典ごとに該当件数が異なるため。
   `assets/templates/report_template_by_source.md`の指摘見出しは`#### {{グループ内通し番号}} [{{severity}}]`
   （例: `#### 2.1.1 [Critical]`、見出しレベル4）であり、手順5の統合レポート側
   `### 5.{{n}} [{{severity}}]`（見出しレベル3）とは番号体系・見出しレベルの両方が異なるため、
   数え直す際はこの出典別レポート自身の見出しレベル4（`grep -c '^#### '`等）で数える。統合
   レポート側の件数をそのまま流用しない）。

   **設計方針の新項目**: 各指摘に、統合レポート5.Nの「互換性の区分」「設計方針との整合」の行と「元の処理の意図と、修正による挙動の変化」のブロックを、内容を変えずに転記する（`design_conflict`が有り、または`alternatives`が書かれた指摘は、「利用者判断事項」を含む代替案のブロックも）。省かない。サマリー表（1節）には足さない（区分別の件数等は統合レポート4節を参照）。「修正後に残るリスクと別経路」のブロックも、統合レポート5.Nと同じ内容で「修正内容の解説」の直後に転記する（統合レポートで省いた指摘は省く）。

   Markdown保存が拒否された場合は、手順5と異なり**指摘全文をテキスト応答に再掲しない**（統合
   レポート側で既に提示済みのため、同じ内容を出典の数だけ繰り返すとテキスト応答が過大になる）。
   代わりに「出典別レポート（<出典名>）の保存は拒否されたため省略。該当指摘は統合レポートの
   file:line一覧を参照: <file:lineの一覧>」のように、統合レポートへのポインタと該当箇所の
   一覧だけを示す。最後に、手順5で保存した統合レポートの末尾に「出典別レポート」節を追記し、
   実際に生成できた出典別ファイルへのパスを一覧で示す。出典別レポートを保存した後（手順7の後）、`references/modes/mode3-report.md`「秘密値の漏れの検査」のとおり`scripts/check_secret_leak.py`を実行し、`RESULT: OK`を確かめる。
