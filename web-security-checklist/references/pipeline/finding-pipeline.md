3. **Red Team起動 → 結果収集 → Blue Team起動（2段階の同期的な流れ）**: 該当する各カテゴリについて、
   まずカテゴリ分のRed Teamサブエージェントを、Agentツールで **同じターンでまとめて** 起動する
   （カテゴリ間の並列実行は問題ない。起動はまとめて行うが、結果は各タスクの完了通知を待って
   非同期に受け取る）。Red Teamの指摘一覧はAgentツールのタスク完了時の戻り値として
   受け取り、その実際のテキストをBlue Teamプロンプトに埋め込んだ上で、続けてBlue Teamサブエージェントを
   起動する。Red Teamの出力をまだ受け取っていない段階でBlue Teamを起動したり、出力を仮定して
   プロンプトを書いたりしないこと。

   **サブエージェント間の通信に関する重要な注意（既知の不具合への対策）**: Red Team/Blue Teamの
   サブエージェントは、進捗確認や結果の受け渡しのために`SendMessage`等でオーケストレータや他の
   サブエージェントへ能動的に連絡しない（`general-purpose`等のエージェント種別名を宛先にした`SendMessage`は
   宛先を解決できず、返信が無関係なセッション〔多くはトップレベル〕に誤着信し、送信元も返信待ちで
   停止したままになる不具合が確認されている）。結果は必ずAgentツールのタスク完了時の戻り値としてのみ返す。
   あなた自身が（ネストされた構成で）サブエージェントとして起動されている場合も同様。オーケストレータも、
   完了は通常のタスク完了通知で待ち、`SendMessage`で催促・pingを送らない。
   ただし、実際に停止・失敗したサブエージェントを`docs/OPERATIONS.md`の手順に
   従って`SendMessage`で再開させることは妨げない。

   **出力の構造化（コンテキストメモリ節約のための共通ルール）**: Red Team/Blue Teamいずれの出力も、
   下記で指定する固定フィールドに限定し、「なぜ重要か」といった背景説明の長文化や、自由記述の
   前置き・まとめの地の文は避けること。目的は情報量を削ることではなく、**同じ事実・根拠・
   具体的シナリオを、より少ない文字数で表現する**ことである。`ReportFindings`ツールが使える文脈では
   フィールドを独自に組み立てず、**必ずそちらのフィールド構成に従うこと**。
   **例外**: `vulnerable_code`（該当コードの実引用）と`fix_suggestion`（修正後コード片）は、
   要約・言い換えで圧縮できないので圧縮対象外だが、
   だからこそ`vulnerable_code`の行数上限（Red Teamプロンプトの骨子を参照）を守り、
   「1指摘あたりコード引用は2箇所（該当コード＋修正案）まで」という範囲に収めること。
   受け取る生テキストが増えるので、下記「結果の即時ファイル永続化」・「Blue Team以降の
   バッチ処理」（モード3手順1）を徹底すること。

   **Red Teamプロンプトの骨子**:
   ````text
   あなたは攻撃者視点でコードの脆弱性を探すセキュリティレビュアーです。
   対象カテゴリ: <カテゴリ名>
   参照基準: references/checklists/principles.md の該当セクション、必要なら references/checklists/database/_index.md,
             references/sources/cwe-top25.md, references/sources/owasp-cheatsheets.md
   対象の差分: <diff>
   関連する既存コード: <呼び出し元・関連ファイル。文脈が要る場合は読みに行ってよい>

   実際に攻撃者ならどう突くかを考え、疑わしい欠陥ごとに次の固定フィールドで報告してください
   （1件に1欠陥。同じ箇所の別の欠陥は別の件。各フィールドは指定の分量に収める）:
   - file/line（複数行にまたがる場合は範囲で。例: routes/account.js:7-17）
   - category (principles.mdのカテゴリ名 + CWE番号のみ。理由の説明はここに書かず、後述の
     root_causeに書く)
   - severity (暫定でよい: Critical/High/Medium/Low。最終判断はArbiterが行う)
   - summary (1文)
   - vulnerable_code（該当箇所の実コードを引用する。要約・言い換えをせず実際のコード片を貼ること。
     目安は最大15行程度。「チェックが存在しない」ことが問題な場合は、本来チェックがあるべき
     周辺コードを引用してよいが、この場合も15行を超えるときは関数シグネチャ＋チェックが
     入るべき行番号のみを示し、詳細説明はroot_causeに譲る（長さの上限より「何が欠けているか」を
     明確に書くことを優先する）。diffの削除側（`-`行）に対する指摘の場合は削除前のコード
     （diffのコンテキストまたは変更前バージョン）を引用する。複数ファイルにまたがる場合は
     ファイルごとに引用を分ける）
   - root_cause（1〜3文。**主語をコードにして**（例:「このコードは〜のため〜が起きる」）、
     何が具体的にまずいかを技術的に説明する。次のfailure_scenarioとは主語で区別する）
   - failure_scenario（1〜3文。**主語を攻撃者にして**（例:「攻撃者が〜を送ると〜」）、
     root_causeを前提にした具体的な入力/操作→結果を書く。CSRFや認可欠如のようにroot_causeと
     内容が近くなる脆弱性では、failure_scenario側に実際に到達可能なエンドポイント名・
     パラメータ名など再現に必要な固有情報を書き、technicalな理由の説明はroot_cause側に譲る
     形で書き分けてよい。憶測ではなく再現可能な形で書く）
   - fix_suggestion（必須。CONFIRMED相当になりうる指摘には**unified diff形式**（変更のない
     前後2〜3行程度はそのまま、削除行の先頭に`-`、追加行の先頭に`+`）で具体的な修正を示すこと。
     `vulnerable_code`と同じコードを全文書き直すのではなく、実際に変わる箇所だけを`-`/`+`で
     示す（読者が「何が変わったか」を一目で分かるようにするため）。新規に丸ごと追加する
     コード（新設ミドルウェア関数等、削除対象がない場合）は全行`+`のdiffで表現してよい
     （正当なunified diffの一形態）。例:
     ```diff
       app.use('/', authRoutes);
     - app.use('/', accountRoutes);
     + app.use('/', requireAuth, accountRoutes);
     ```
     「要検討」で済ませてよいのは、修正方法がこのSKILLの範囲外の意思決定を要する場合
     （例: 仕様不明のため要ヒアリング）に限り、その理由も明記する。単に時間を節約する目的で
     「要検討」を使わないこと — Blue Teamが`fix_suggestion_check`で「要検討」を空/曖昧と
     同様に扱い具体化を試みるため、安易に使うと手戻りになる）
   - （指示書で`references/design/design-fields.md`を渡されたときのみ）同ファイルの項目
   確証が持てないものも「要検証」として含めてよい。過検出を恐れず広めに拾うこと（フィールドの
   分量は絞っても、拾う指摘の件数自体は絞らない）。
   CVEのPoCを試せなかった・再現しなかったことを理由に指摘を落とさない（「再現しなかった」で下げてよいのは、アプリが読む入力へ送り、陽性対照かコード根拠で到達と影響の観測を確認し、記録を残した場合だけ。他は「未検証」）。
   ````

   **Blue Teamプロンプトの骨子**:
   ```text
   あなたはRed Teamが出した脆弱性指摘を検証する役割です。誤検知を見抜き、実際に悪用可能かを
   実コードの文脈（呼び出し元、ミドルウェア、既存のサニタイズ処理等）を確認した上で判定してください。
   Red Teamの指摘一覧: <Red Teamの出力>
   対象リポジトリの関連コード: <必要な範囲>
   （上記は最小限の範囲。不足があれば呼び出し元・ミドルウェア・バリデーション定義を自分で
   Read/Grepしてよい）

   各指摘について、次の固定フィールドで判定してください（長い解説文は避け、簡潔に）:
   - verdict: 以下のいずれか
     - CONFIRMED: 実際に悪用可能、または明確にチェックリスト未達
     - REFUTED: 誤検知（理由を明記。例:「上位ミドルウェアで既にエスケープ済み」）。他の指摘の
       修正で一緒に直る、引用範囲の一部が外れる、は理由にしない（当たる行で判定する）
     - PLAUSIBLE: 悪用可能性は否定できないが、確証を得るには追加情報や人間の判断が必要
   - evidence（1〜3文。verdictの判定理由となった実コードの文脈を簡潔に。「なぜこの verdict に
     なるか」の説明であり、次のvulnerable_code_checkとは役割が異なる — 重複して同じコードを
     長々と引用しない）
   - vulnerable_code_check（CONFIRMED/PLAUSIBLEの場合のみ必須。Red Teamが引用した
     `vulnerable_code`が実際のファイル内容と一致しているかを実際に読んで確認し、ずれていれば
     実際のコードに訂正する。差分がまだリポジトリに存在しない新規ファイルを追加するものである
     場合は、その差分内容自体を「実際のファイル内容」とみなして照合する。REFUTEDの場合は
     「REFUTEDのため省略」でよい）
   - fix_suggestion_check（CONFIRMED/PLAUSIBLEの場合のみ必須。Red Teamの`fix_suggestion`が
     実際にこのリポジトリの構成（既存のライブラリ・ミドルウェア等）に照らして妥当か確認し、
     不十分ならより具体的な修正コードに補強する。**ファイル見出しと`@@ -行,数 +行,数 @@`（実際の行番号）付きのunified diffで**
     検証・補強すること。`fix_suggestion`が空・曖昧・
     「要検討」・diff形式になっていない（全文コードのまま）のいずれかの場合は、実装可能な
     具体的コードへの置き換え、またはdiff形式への書き直しを試みること。それでも書けない場合のみ
     理由を添えて「要検討」を維持してよい。REFUTEDの場合は「REFUTEDのため省略」でよい。
     **この確認は次の3点を明示的に行い、`合格`/`不合格`の形で判定を残すこと**（詳細は「修正案
     監査レビューの厳格度」節を参照。この判定はArbiterが5eでそのまま「標準」厳格度の監査結果と
     して採用するため、確認内容が分かる粒度で書く）: ①構文的妥当性（対象言語として明らかな構文
     エラーがないか）、②既存コードとの整合性（実際に存在するライブラリ・ミドルウェア・変数名等を
     前提にしているか）、③脆弱性の解消（適用した場合に`failure_scenario`で示した攻撃が実際に
     防げるか）を確認する）
   - needs_repro（任意。再現が要る入力・経路を1文で。無ければ「なし」）
   - （同上。REFUTEDは省略）同ファイルの項目
   読取専用で再現は実行できない。「再現しなかった」を根拠にverdictを下げない（条件はRedと同じ。満たさなければ「未検証」）。
   ```

   **結果の即時ファイル永続化（コンテキストメモリ節約）**: Red Team・Blue Teamそれぞれの結果を
   受け取ったら、オーケストレータはその生テキストを会話コンテキストに溜め込み続けるのではなく、
   直ちに対象リポジトリ外（例: このセッションのスクラッチパッドディレクトリ。無ければ対象リポジトリ外の
   一時ディレクトリ）へ、カテゴリ単位のデータファイルとして保存する。**形式はJSON Lines
   （全カテゴリ分を1行1指摘で`findings-log.jsonl`に追記）またはMarkdown見出しを持たないプレーン
   テキストを推奨する**。実地検証（`web-security-checklist-workspace/context-mitigation-test/`、
   `iteration-3/`）で、`#`/`##`見出し＋CWE/深刻度/攻撃シナリオを伴う「所見レポート」然とした
   Markdown構造のファイル（`findings-<カテゴリ名>.md`等）はWriteツールに拒否される場合と
   されない場合の両方が観測されており、非決定的な挙動と考えられる一方、同じ内容をJSON Lines
   （`findings-log.jsonl`）やプレーンテキスト（見出しなしの`.txt`）で保存した場合はこれまでの
   実行を通じて一貫して成功している。このため（拒否が保証されているからではなく、単純により
   確実な形式として）カテゴリ単位のMarkdownレポートファイルは**使わない**こと。
   ファイル名には「report」「summary」等の要約・レポートを想起させる語も避け、データファイルらしい
   名前を使う。保存後は、会話コンテキスト上でその生テキストを再度引用・再言及せず、
   「<カテゴリ名>の結果を保存済み（ファイル: <パス>）」という短い確認だけを残す。保存が拒否された
   場合は、「全モード共通の原則」（`references/core/common-principles.md`）の「ツールに拒否されたら別の手段で回避しない」原則に従い
   （Bashのheredoc等で回避しようとしない）、拒否された旨を記録した上で、やむを得ず上記の構造化
   フォーマットのまま会話コンテキストに保持する。
